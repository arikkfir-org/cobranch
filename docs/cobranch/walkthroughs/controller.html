Structure

Three engines behind one three-method interface

controller.Runner is Dispatch, Follow, Sweep. The runner and the deliverer are also a Scheduler. With jobs.pods off, each engine gets a NoPods cluster and only webhook jobs run.

One pass

Start up to 50, then follow everything that works

  • Claim is the queue. A queued row whose lease is due is taken with FOR UPDATE SKIP LOCKED and given a new lease_until. A replica that dies only delays its rows until the lease expires.
  • No room is not a failure. When the namespace's quota is full, Defer puts the row off with the reason, which the Console shows.
  • Every pod gets a token of its own, minted at dispatch: cbr_ for a run, cba_ for a task, cbd_ for a render. The pod calls the REST API with it, as its own principal (tokens).
  • Ending twice ends once. Finish and MarkRunning report whether they changed anything, so two replicas following one pod do no harm.
  • Sweep cleans what ended otherwise: pods of runs that were cancelled or superseded, expired tokens, old schedule slots, old renders.

Isolation

Where the pods run

  • A namespace per organization, made with its first run or task (jobcluster.Prepare). Its NetworkPolicies admit no ingress, and egress only to DNS, the internet, and the installation's REST, GraphQL and Git servers.
  • Delivery targets are fenced separately. In the installation's own cluster, incluster makes each environment's namespace and applies as an account bound there alone. In another cluster, remote opens the kubeconfig an organization secret holds, from addresses the chart's values admit.
  • Outbound calls are filtered. egress refuses webhook receivers and cluster addresses inside ranges the operator excludes.

Worth a closer look

One loop, written three times

Each engine has dispatch.go, follow.go, nopods.go, and a Store with Claim, Token, Defer, a mark-running and a finish. The differences are real (restarts, apply, webhooks) but sit on top of a shared skeleton that isn't shared.

jobcluster serves three masters

One adapter implements runner.Cluster, taskrunner.Cluster and deliverer.Pods with parallel methods: Start, StartTask, StartRender; Pods, TaskPods, Renders; Remove, RemoveTask, RemoveRender. One pod port with a kind?

Settings repeat

Pods, Lease, RoomRetry, Vanished, RESTURL and GitURL are copied into three Settings structs in controllerLoops.
