Cobranch architecture

Four zoom levels: the running system, the one binary, the layers, and the packages by how central they are. It ends with places that look worth a targeted review for duplication and reuse. Each workload, the database and the two web apps have a page of their own.

Level 1 · the running system

Ten workloads over one store

Everything durable is in PostgreSQL, Git packs included unless the operator names a bucket. No broker, no leader: replicas claim rows with FOR UPDATE SKIP LOCKED. Only the Git server touches Git objects, and only the controller makes pods.

A push, end to end. The synchronous part ends when PostgreSQL commits; everything after is rows being claimed.

Review leads

Places to look first

These come from structure and a skim, not a line-by-line read. Each is a question to answer in a targeted pass, not a verdict.

1 · Three pod loops with one shape

runner, taskrunner and deliverer each carry dispatch.go, follow.go, nopods.go, Follow and Sweep. The two later ones already borrow runner.Pod and runner.ErrNoPods. Is there one claim-start-follow-sweep loop underneath?

2 · Two transports, written twice

rest (7.2k) and graphql (6.2k) mirror each other file for file: activity, agents, chats, code, tokens, usage. The Console calls only REST. How much mapping, cursor and error code could they share?

3 · services/code holds five subjects

5.9k lines in 50 files: browsing, annotations and branch status, merges, reviews, job settings, triggers, runs and logs, environments and deliveries. Meanwhile jobs is 0.7k and delivery 0.3k. Are the boundaries where the names say?

4 · Cursors rolled by hand

Separate encode and decode pairs in issues, code/history, code/reviews, rest/activity, graphql/activity, graphql/chats, graphql/jobs and adminapi. One opaque-cursor helper?

5 · Every store, implemented twice

5.8k lines of in-memory fakes (*test packages) shadow the 11.6k PostgreSQL stores. Do both pass one contract suite, or can they drift?

6 · Store plumbing repeats

Five stores (auth, orgs, repos, secrets, artifacts) each define an identical transact method over the package's one. 101 files in one package suggests more row-to-domain boilerplate worth a look.

7 · Six kinds of token

Prefixes cba_, cbd_, cbk_, cbp_, cbr_, cbs_ across auth, agents, runner and deliverer. Resolving is one switch in auth.Service.Authenticate; minting and hashing still live in four packages.

8 · The web apps share nothing yet

The Back-office is one 568-line HTML file beside the Console's 48 lib/ modules; web/ui is still planned. In the Console, api.js answers a response two ways, and chats surface through three REST files.

9 · Domain logic inside adapters

followPush orchestrates what a push sets off from inside adapters/postgres/git.go, and gitserver/facts.go holds rules about refs. Both read like service code. See push-worker and git-server.

10 · The database wrapper against the house rule

Scopes pin the organization for every query and Transact names the acting principal; a read names nobody, and nothing sets the trace. See PostgreSQL.
