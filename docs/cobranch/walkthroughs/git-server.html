Workload · cobranch git-server

git-server: the only one that touches Git

Clone, fetch and push over HTTPS and SSH, and every read of code the APIs make. It keeps no repository on disk: each request builds a throwaway one, with its refs from one PostgreSQL query and its packs hard-linked from the pod's disk cache, which downloads a pack from the object store only the first time it is asked for, and a push is committed to PostgreSQL before Git answers the client.

A fetch

Every request serves a repository built for it

A pack's name is the hash of its content, so the cache keeps it by name whichever upload it came from. A fetch hard-links what it serves, so the cache may evict any file at any time without breaking a fetch in flight.

A push

The pre-receive hook is this same binary, calling home

  • One transaction decides. git.Record locks the repository's live branches, refuses a push whose refs moved meanwhile (StaleError), lists the pack, inserts the push and its commits, and notifies. A refused push changes nothing.
  • The pack is uploaded before it is listed. A push that fails leaves files no row lists; maintenance deletes them.
  • Branch facts are counted here, in the hook's call: merge requirements from /cobranch.yaml, the AI reviewer's settings, and each live branch's standing against the default branch (facts.go). A file that does not parse at the default branch's new tip refuses the push.
  • Quota is weighed twice: before the upload, to avoid storing what won't fit, and again inside the transaction, which alone is sure.
  • What follows a push is not here. Attribution, runs, deliveries, reviews and branch status belong to the push-worker.
The internal API

How the API servers read code

On the internal port, under gitinternal.ReposPath. Each call carries the viewer's own token, and the Git server authorizes it itself. Both ends are the same binary, so they share one Go type per body.
