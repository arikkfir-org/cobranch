Back-office: the operator's console

Where an installation's administrators see every organization and user, set limits, and manage sign-up and identity providers. It is one HTML file with no build step, served by Caddy, calling the admin-server.

How it loads

One page, one config call, one API

The page routes in the browser, so a page at any depth asks for config.json beside itself and every directory answers it. The design system's tokens, typefaces and marks come from assets/, the same files the Console draws with.

Shared inside the file: api (fetch with the cookie, problem details to errors, ETag out and If-Match in), h (a DOM builder), go and route (history routing), list (a searched, paged table that follows next links), and showSignIn.

Things to know

How it stays safe to change

  • Stale edits are refused. Every PATCH and DELETE sends the ETag it read; a 412 tells the administrator someone changed it first.
  • Mutations are JSON from its own origin, which the Admin API's cookie guard requires, merge patches included.
  • Sign-in returns here. The Auth server accepts the Back-office's URL as a return target (SafeReturn) only because the installation names it.
Review leads

Worth a closer look

A second copy of the Console's base

api, h, go, route, showCard, showSignIn and the formatters re-implement lib/api.js, dom.js, router.js, layout.js and format.js. web/ui, planned for exactly this, does not exist yet.

Styles outside the component stylesheet

The page uses the design system's tokens but carries 130 lines of its own component CSS, where the Console's rule is that a page writes none. Sharing components.css would close the gap.

Two ways to learn the configuration

The Back-office fetches config.json; the Console has it templated into its page and keeps config.json only for old releases. One mechanism for both.
